# Craft Agents v0.18.0 架构调整建议

> 角色：产品架构审查员
> 基线：v0.17.0（commit f43c1572）
> 目标定位：以 Project 为核心、拥有长期 Memory、Browser 环境和 Workflow 执行能力的个人 AI 工作空间
> 约束：不增加功能数量；优先减少复杂度、提高一致性
> 日期：2026-07-26
> 性质：只读分析，未修改任何代码

---

## 一、现状分析

### 1.1 真实架构

Craft Agents 是一个基于 `craft-ai-agents/craft-agents-oss` 二开的 Bun monorepo，桌面优先。

**仓库结构**：4 apps + 9 packages

| 层 | 成员 | 角色 |
|---|---|---|
| apps | `electron`（核心）、`webui`（renderer 的浏览器投影，靠 alias 复用）、`viewer`（独立分享站）、`cli`（终端客户端） | 应用壳 |
| 共享层 | `core`（**空壳**，仅 types+utils）、`shared`（**上帝包**，30+ 子目录）、`session-tools-core`、`ui` | 逻辑与类型 |
| 运行时层 | `server-core`（可复用基建）、`server`（薄入口壳）、`pi-agent-server`（Pi 子进程）、`session-mcp-server`（会话工具 MCP 子进程） | 进程 |
| 子系统 | `messaging-gateway`（飞书/微信，**深度依赖 server-core**） | 消息接入 |

**三类进程**：
1. 主进程：Electron main（桌面）或 headless server（Bun），都基于 `server-core`
2. `pi-agent-server`：spawn 子进程，JSONL over stdio，包裹 `@earendil-works/pi-coding-agent` SDK
3. `session-mcp-server`：stdio MCP 子进程，给 Codex 提供会话级工具（SubmitPlan 等）

**存储**：纯文件系统，无数据库。`~/.craft-agent/workspaces/{slug}/` 下分布 sessions.jsonl、projects/、cognition/、library/ 等。

### 1.2 核心数据流（用户消息 → LLM 响应）

```
客户端(electron renderer / webui / cli)
  ──WebSocket-RPC──▶ SessionManager (server-core)
                        │
                        ▼
                   AgentBackend.factory  ──按 provider 分流──┐
                        │                                    │
            ClaudeAgent(进程内)                        PiAgent(spawn 子进程)
                        │                                    │
                        └──── runtime-resolver 启动 session-mcp-server 子进程 ────┘
                                                │
                                                ▼
                                   会话工具回调经 stderr __CALLBACK__ 协议回主进程
                                                │
                                                ▼
                          持久化: shared/sessions/storage.ts → session.jsonl
```

### 1.3 用户主要使用路径（现状）

以 **Session 为中心**，Project 是二级属性：

```
左侧导航
  ├─ 探索(会话/网页双模式首页 + Today)
  ├─ 浏览器(独立工作区，workspace 级)
  ├─ 会话列表 / 看板(按状态分组)
  ├─ Projects(可展开，但 renderer 仅 85 行，能力单薄)
  ├─ Library
  └─ 插件
        │
        ▼
  会话主区(对话) + 右侧审阅栏(信息/文件/终端/来源/画布/Widget)
```

Project 详情页仅 4 tab（Sessions/Assets/Memory/Settings），新建会话才是主操作入口。

### 1.4 当前架构是否支持 Project-centric？—— 类型层支持，能力层不支持

| 维度 | 类型层 | 能力层 | 差距 |
|---|---|---|---|
| Project 实体 | ✅ `ProjectConfig`（id/slug/workingDirectory/details/MEMORY.md） | ❌ 仅 750 行代码，renderer 85 行 | 缺 members/权限/source 绑定/默认设置/icon |
| Session→Project | ✅ `SessionConfig.projectId` + 绑定/移动/解绑 | ✅ 完整 | UI 以会话列表为中心，非项目 |
| Memory | ✅ MEMORY.md 项目级 | ⚠️ 双轨：MEMORY.md(project) + Cognition(workspace) | Cognition 不按项目隔离 |
| Browser | ❌ DTO 无 projectId | ❌ 纯 workspace 级 | 认知事件层已预留 projectId 但 4 个调用点从未透传 |
| Workflow | ❌ 无统一概念 | ❌ Automation + Task DAG + Checkpoint + Cognition Loop 四套 | 概念碎片化 |
| Library | ✅ 数据层有 projectId | ⚠️ 查询层缺 projectId 过滤 | 无法"列出项目 X 的文档" |

**结论**：Project 已是一等公民的"类型骨架"，但记忆、浏览器、工作流三条线全部停留在 workspace 级。向 Project-centric 升级的核心工作是**把这三条线的 scope 从 workspace 下沉到 project**，而非新建概念。

| 冲突项 | 冲突原因 | 处置 |
|---|---|---|

### 3.4 高成本低价值模块

| 模块 | 成本 | 价值 | 处置 |
|---|---|---|---|
| Task DAG（P4 延迟执行） | 3,075 行 + 复杂控制流解析 | 未完成、低使用 | 合并入 Workflow 或**冻结** |
| messaging-gateway 框架扩展层 | 15,406 行，深度耦合 server-core | 个人定位下仅 2 adapter | **冻结**扩展，最小化维护 |
| Onboarding 完整流程 | 1,755 行 | 一次性 | **精简**为最小引导 |

### 3.5 断舍离结论

**删除**：
- `apps/viewer`（独立分享站）
- `apps/cli`（终端客户端，澄清保留 `packages/craft-cli`）
- Task DAG 未完成的 P4 控制流执行（或整体合并入 Workflow）

**合并**：
- `Automation` + `Task DAG` + `Checkpoint` + `Cognition Loop` → **Workflow**
- `Explore Brief` + `Today` + `Guidance` → **项目 Activity**
- `右侧审阅栏` + `会话信息面板` → **Context Panel**
- `MEMORY.md` + `Cognition` → **project-scoped Memory**

**保留**：
- Agent 引擎、SessionManager（拆分后）、Session 存储
- Project 实体（大幅增强）
- MCP、认证、配置、协议
- Browser（拆分 + 下沉后）、Library、Git、插件、Skills、可视化

## 四、v0.18 架构建议

### 4.1 设计原则

1. **Project 为唯一作用域容器**：Memory/Browser/Workflow/Chat 全部 project-scoped
2. **不新增功能**：只做下沉、合并、拆分
3. **减少概念数量**：4 套任务 → 1 套 Workflow；3 套建议 → 1 套 Activity；2 套面板 → 1 套 Context Panel
4. **一致性优先**：所有能力统一以 `{workspace}/projects/{slug}/` 为存储根

### 4.2 五大模块关联

```
┌─────────────────────────────────────────────────────────────┐
│                      Workspace                               │
│  ┌───────────────────────────────────────────────────────┐  │
│  │                    Project (核心容器)                  │  │
│  │  config.json · workingDirectory · details · members   │  │
│  │                                                       │  │
│  │  ┌─────────────┐  ┌─────────────┐  ┌──────────────┐  │  │
│  │  │   Memory    │  │  Workflow   │  │   Browser    │  │  │
│  │  │ (显式+派生) │  │ (统一执行)  │  │ (项目隔离)   │  │  │
│  │  │             │  │             │  │              │  │  │
│  │  │ MEMORY.md   │  │ Automation  │  │ Profile      │  │  │
│  │  │ Cognition   │  │ Task DAG    │  │ History      │  │  │
│  │  │ Activity    │  │ Checkpoint  │  │ Extensions   │  │  │
│  │  └──────┬──────┘  └──────┬──────┘  └──────┬───────┘  │  │
│  │         │                │                │          │  │
│  │         └────────────────┼────────────────┘          │  │
│  │                          ▼                            │  │
│  │                   ┌─────────────┐                     │  │
│  │                   │    Chat     │                     │  │
│  │                   │ (会话视图)  │                     │  │
│  │                   │ Session[]   │                     │  │
│  │                   │ Context     │                     │  │
│  │                   │ Panel       │                     │  │
│  │                   └─────────────┘                     │  │
│  └───────────────────────────────────────────────────────┘  │
│  Library (project-scoped) · Plugins · Skills · Sources      │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 五大模块定义

| 模块 | 职责 | 存储根 | 核心改动 |
|---|---|---|---|
| **Project** | 唯一作用域容器；持有 workingDirectory/details/members/默认设置 | `{workspace}/projects/{slug}/` | 增强：补默认 model/source/权限/icon；renderer 从 85 行扩为完整工作空间入口 |
| **Memory** | 项目级长期记忆；MEMORY.md（显式）+ Cognition（派生）+ Activity（动态） | `{workspace}/projects/{slug}/memory/` + `cognition/` | 下沉：Cognition 从 workspace 级改 project 级；统一检索接口 |
| **Workflow** | 统一执行抽象；Automation=触发器、Task=执行图、Checkpoint=节点、Loop=状态机 | `{workspace}/projects/{slug}/workflows/` | 合并：4 套任务系统收敛为 1；绑定 projectId |
| **Chat** | 项目内会话视图；Session 退为 Project 子资源 | `{workspace}/projects/{slug}/sessions/` | 降级：Session 从一等公民退为 Project 子视图；UI 默认入口从会话列表改为项目 |
| **Browser** | 项目隔离浏览器环境；Profile/历史/扩展按 project 分区 | `{workspace}/projects/{slug}/browser/` | 下沉：DTO 加 projectId；4 个 emit 调用点透传；profile 按项目分区 |

### 4.4 关键收敛点

- **存储统一**：所有 project-scoped 数据落 `{workspace}/projects/{slug}/` 下，消除 workspace 级散落
- **UI 重心转移**：默认导航从"会话列表"改为"项目列表 → 项目工作空间"；会话成为项目内的 tab
- **Context Panel 统一**：右侧审阅栏 + 信息面板合并，按当前 project/session 作用域聚合 Memory/Workflow/Browser/来源
- **Activity 统一**：Brief/Today/Guidance 三轨合并为项目动态流，纯增量替换

## 五、风险分析

### 5.1 如果继续现状架构发展，最大技术债

| # | 技术债 | 严重度 | 后果 |
|---|---|---|---|
| 1 | **上帝对象**：`SessionManager.ts` 9,656 行、`browser-pane-manager.ts` 5,597 行 | 🔴 极高 | 任何改动风险巨大、测试困难、认知负担高、merge 冲突频发 |
| 2 | **上帝包**：`shared` 30+ 子目录混装 agent/config/sessions/cognition/library/automations/projects | 🔴 极高 | 边界模糊、循环依赖隐患、构建慢、无法独立测试 |
| 3 | **包边界混乱**：`core` 空壳；`shared`/`server-core` 同名目录重叠（sessions/tasks/cognition/library/privacy）；`pi-agent-server` 越界 `../../shared/src/` 直引 | 🟠 高 | 依赖方向不可控、重构牵一发动全身 |
| 4 | **概念碎片化**：task/loop/checkpoint/todo 四套任务语义；brief/today/guidance 三套建议 | 🟠 高 | 用户认知混乱、开发重复实现、数据不一致 |
| 5 | **scope 错位**：Memory/Browser/Workflow 全 workspace 级，与 Project-centric 目标矛盾 | 🟠 高 | 每个新功能都要补 project 维度，债务滚雪球 |
| 6 | **Messaging 深度耦合**：`messaging-gateway` 依赖 `server-core` 而非 core/shared | 🟡 中 | 无法独立部署、拖累 server-core 重构 |

### 5.2 必须提前重构的点（v0.18 前置）

**P0 — 不重构则 Project-centric 无从落地**：

1. **SessionManager 拆分**：按职责拆为 SessionLifecycle / MessageProcessor / ToolDispatcher / PersistenceCoordinator / EventEmitter。9,656 行 → 每个 ≤ 2,000 行。
2. **引入 Project scope 层**：在 workspace 与 session 之间建立 project 作用域，所有 project-scoped 数据迁移到 `{workspace}/projects/{slug}/`。这是 Memory/Browser/Workflow 下沉的前提。
3. **Browser projectId 透传**：DTO 加字段（v0.16.2 已规划）+ 4 个 emit 调用点透传。最小改动、解锁项目隔离。

**P1 — 重构窗口期应一并完成**：

4. **browser-pane-manager 拆分**：按 Lifecycle / Layout / Extensions / Downloads / Passwords / Profile 拆分。5,597 行 → 每个 ≤ 1,500 行。
5. **Workflow 统一抽象**：Automation + Task DAG + Checkpoint + Cognition Loop 合并为单一 Workflow 概念，绑定 projectId。
6. **shared 拆包**：按领域拆为 `@ca/agent`、`@ca/sessions`、`@ca/cognition`、`@ca/library`、`@ca/automations`、`@ca/projects` 等独立包，消除上帝包。

**P2 — 可在后续版本渐进**：

7. Context Panel 合并（right-sidebar + info）
8. Activity 统一（Brief + Today + Guidance）
9. messaging-gateway 解耦（依赖 core/shared 而非 server-core）
10. `pi-agent-server` 越界引用正式化为 workspace 依赖

### 5.3 重构顺序建议

```
Phase 1 (P0): Project scope 层 + SessionManager 拆分 + Browser projectId
              ↓ 解锁 Memory/Browser/Workflow 下沉
Phase 2 (P1): browser-pane-manager 拆分 + Workflow 统一 + shared 拆包
              ↓ 消除上帝对象/包，概念收敛
Phase 3 (P2): Context Panel + Activity + Messaging 解耦 + 清理 C 级模块
              ↓ UI 一致性、维护成本下降
```

## 六、结论：《Craft Agents v0.18 架构调整建议》

**核心判断**：Craft Agents 的 Project-centric 转型**不需要新建概念**——Project 实体、Session.projectId、Cognition 事件 projectId、Library projectId 数据层均已就绪。真正的缺口是**三条能力线的 scope 下沉**（Memory/Browser/Workflow 从 workspace → project）和**两个上帝对象的拆分**（SessionManager / browser-pane-manager）。

**v0.18 一句话目标**：把"会话为中心 + workspace 级能力"重构为"项目为中心 + project 级能力"，同时偿还上帝对象/包债务，不新增功能。

**必做三件事**：
1. 建立 Project scope 层，统一 `{workspace}/projects/{slug}/` 存储根
2. 拆分 SessionManager（9,656 行）与 browser-pane-manager（5,597 行）
3. 合并四套任务系统为单一 Workflow，绑定 projectId

**必删两件事**：
1. `apps/viewer`（与方向无关）
2. `apps/cli`（个人桌面定位冗余）

**衡量标准**：v0.18 完成后，新建一个 Project 应能自动获得独立的 Memory / Browser Profile / Workflow 上下文，而非依赖 workspace 级共享；SessionManager 与 browser-pane-manager 各拆分件均 ≤ 2,000 行；`shared` 拆为 ≤ 8 个领域包。
